# user-auth Specification

## ADDED Requirements

### Requirement: 登录与登出提供页面表单路由
系统 SHALL 在页面路由上提供与 API 等价的登录/登出能力：GET 登录页渲染表单，POST 登录表单成功后建立会话并重定向到仪表盘；登出通过页面表单/路由完成并重定向回登录页。页面路由遵循"未认证访问受保护页面 → 302 到登录页"的语义（而非 401 JSON）。

#### Scenario: 表单登录建立与 API 等价的会话
- **WHEN** 用户通过页面表单以正确凭据登录
- **THEN** 会话中 SHALL 写入与 API 登录一致的用户信息（user_id、username、role、class_id、生效班级），后续页面请求均被识别为已登录

#### Scenario: 错误凭据不区分原因
- **WHEN** 页面表单提交了错误密码或不存在的用户名
- **THEN** 页面 SHALL 显示统一的失败提示，不指明具体原因，与 API 端点的防枚举语义一致

#### Scenario: 未登录访问页面路由重定向而非 401
- **WHEN** 未登录用户访问仪表盘等受保护页面路由
- **THEN** 系统 SHALL 302 重定向到登录页

## MODIFIED Requirements

### Requirement: 预置种子账号在首次部署时自动可用
系统 SHALL 在首次启动时自动写入预置的班级与用户数据，使测试/演示账号立即可登录。预置数据 SHALL 覆盖两个班级（class-001 与 class-002），每个班级含教师、学生与样本材料；教师 SHALL 通过任教关系（teacher_classes）可切换到其任教的班级。对已初始化的数据库，系统 SHALL 执行幂等补种：仅插入缺失的预置行，绝不修改或删除任何已存在的用户、材料或其他数据。

#### Scenario: 首次部署后预置账号可登录
- **WHEN** 全新部署后的应用完成首次启动
- **THEN** 预置的教师账号和至少两个学生账号能够使用文档载明的初始密码成功登录

#### Scenario: 种子数据仅在数据库为空时写入
- **WHEN** 应用启动时检测到数据库中已存在预置用户记录
- **THEN** 系统 SHALL 跳过对既有数据的任何覆盖或修改，仅按自然键判重补插缺失的预置行

#### Scenario: 全新部署后双班账号均可登录
- **WHEN** 全新部署后的应用完成首次启动
- **THEN** class-001 的预置教师/学生账号与 class-002 的预置教师/学生账号均能使用文档载明的初始密码成功登录

#### Scenario: 教师具备跨班任教关系供切换演示
- **WHEN** 全新部署后查询预置教师的任教关系
- **THEN** 至少一名教师 SHALL 同时任教 class-001 与 class-002，且两个班级各有自己的样本材料（供班级隔离验证）

#### Scenario: 旧库升级触发幂等补种
- **WHEN** 应用启动时数据库已存在用户与材料数据（如旧版本部署的 volume）
- **THEN** 系统 SHALL 保留全部既有数据不动，仅补插缺失的预置账号、样本材料与任教关系；补种后新旧账号均可登录

#### Scenario: 重复启动不产生重复数据
- **WHEN** 同一数据库多次重启应用
- **THEN** 预置用户、样本材料与任教关系 SHALL 不被重复插入（以用户名/（教师,班级）等自然键判重）
